# API ChargeGrid v1

Base `/v1`, JSON, UUIDs e datas UTC ISO 8601. Bearer JWT de pessoa nas rotas de domínio, logout e alteração de senha; cadastro, login, refresh, solicitação de recuperação e verificação por código são públicos com limite de tentativas. Sync usa `Authorization: Device <chave>`. Erro: `{"error":{"code":"point_unavailable","message":"Ponto indisponível"}}`. Validação retorna 422. Respostas de listas: `{"items":[],"total":0,"limit":50,"offset":0}`. `GET .../current` retorna recurso ou `null`.

Auth: POST `/auth/register` {email,password,name,account_type?:"consumer"|"vendor"}; `/auth/login` {email,password}; `/auth/refresh` {refresh_token}; `/auth/logout` com Bearer. O tipo de conta é escolhido no cadastro e o padrão para clientes antigos é `consumer`; login não recebe tipo. Cadastro novo sem confirmação pendente, login e refresh retornam `{access_token,refresh_token,expires_in,token_type:"bearer",user:{id,email}}`. Cadastro inclui `requires_email_confirmation`, calculado conforme a resposta do provedor: `false` com sessão imediata, `true` quando a conta depende de confirmação. Cadastro de e-mail já existente recebe resposta neutra sem sessão, sem afirmar que uma mensagem foi enviada. Senhas são preservadas exatamente, inclusive espaços; cadastro e nova senha exigem 8–128 caracteres, login aceita 1–128 para compatibilidade com contas legadas. O provedor pode recusar senhas fracas. Os endpoints `/auth/verify-email` e `/auth/resend-signup` permanecem compatíveis, embora o projeto atual não exija confirmação.

Recuperação: POST `/auth/password/forgot` {email} solicita e-mail com link; `/auth/password/reset` {email,code,password} mantém suporte a código OTP. O link padrão abre `/auth/confirmed`, fora da base `/v1`, que apresenta o formulário quando recebe `type=recovery` e o token no fragmento da URL. A página remove o fragmento imediatamente, mantém o token apenas em memória e chama POST `/auth/password/update` {password} com Bearer válido. Ambos os fluxos de redefinição revogam as sessões de atualização no provedor e pedem novo login. Tokens de acesso já emitidos podem permanecer válidos até sua expiração. A entrega de e-mail ainda depende do SMTP configurado no Supabase; indisponibilidade ou limite do provedor retornam erro, não uma confirmação falsa de envio.

`GET/PATCH /me`: `{id,name,account_type,phone,vehicle_description,operator_enabled,created_at}`; PATCH aceita apenas name,phone,vehicle_description. `account_type` é persistido no primeiro acesso a partir dos metadados do cadastro e não é alterado por logins posteriores. Escolher `vendor` não habilita `operator_enabled`: a gestão de postos exige aprovação administrativa. Contas de vendedor pendentes podem usar recargas. Na migração, operadores existentes recebem `vendor`, demais perfis recebem `consumer`. `GET /me/summary`: `{month:"YYYY-MM",currency:"BRL",estimated_cost,energy_wh,sessions_count}` para sessões encerradas com carga no mês civil de São Paulo; custo é estimativa, não pagamento.

`GET /stations` filtros lat,lng,radius_km,limit,offset; `GET /stations/{id}`. Posto: `{id,owner_id,name,address,latitude,longitude,active,connectors:[]}`. Ponto: `{id,station_id,public_code,connector_type,power_kw,price_per_kwh,max_duration_minutes,active,control_version,available,online,physical_state}`.
POST `/stations` {name,address,latitude,longitude}; PATCH aceita esses campos e active. POST `/stations/{id}/connectors` {public_code,connector_type,power_kw,price_per_kwh,max_duration_minutes}; PATCH `/connectors/{id}` aceita campos e active. Escrita exige operador aprovado/proprietário.

POST `/connectors/{id}/device`, `/devices/{id}/rotate-key`: `{device_id,device_key}` chave mostrada uma vez. POST `/devices/{id}/revoke`: `{revoked:true}`.

GET `/connectors/{id}/device`, exclusivo do operador aprovado proprietário do posto: `{device_id,connector_id,firmware_version,last_seen,online,physical_state,connected,reconciled}`. Permite reencontrar o dispositivo para rotação ou revogação depois de fechar a tela; nunca devolve chave nem hash. Retorna 404 quando não existe dispositivo ativo, inclusive após revogação, ou quando o ponto pertence a outro operador; consumidores e vendedores pendentes recebem 403.

POST `/reservations` {connector_id}, header `Idempotency-Key` obrigatório; 202 reserva `{id,user_id,connector_id,status,created_at,confirmation_deadline,expires_at}`. Estados pending_device,confirmed,cancelling,cancelled,expired,consumed. GET `/reservations/current`; POST `/reservations/{id}/cancel` 202 mesma representação.

POST `/charging-sessions` {public_code,reservation_id?:UUID,coupon_code?:string,max_duration_minutes:30,max_cost?:decimal} Idempotency-Key obrigatório; 202 sessão. POST `/charging-sessions/{id}/stop` mesmo header, 202. GET `/charging-sessions/current`, `/{id}`, `/me/charging-sessions`, `/stations/{id}/charging-sessions` (proprietário). Sessão: `{id,user_id,connector_id,reservation_id,status,created_at,started_at,ended_at,max_duration_minutes,max_cost,price_per_kwh,discount_percent,energy_wh,soc_percent,source,last_measurement_at,cost_estimate,end_reason,online}`. Históricos são ordenados por `created_at` decrescente, com UUID apenas para desempate; registros antigos usam início/fim conhecido como data de criação aproximada. Estados starting,charging,stopping,completed,failed,interrupted. Uma tentativa que nunca iniciou termina como `failed`; reinicialização após início termina como `interrupted`. SoC ausente é null. GET `/operator/summary`: `{stations,total_sessions,total_energy_wh,total_estimated_cost}`.

GET `/coupons` filtro station_id; POST {code,description,discount_percent,station_id?:UUID,valid_until}; PATCH `/coupons/{id}` aceita description,discount_percent,valid_until,active. Cupom global vale somente nos postos de seu operador. Valores monetários serializados como strings decimais; nenhum pagamento real.

Idempotência reserva/início/parada: mesmo usuário/operação/chave/corpo devolve recurso original; corpo diferente retorna 409. Cancelamento é naturalmente idempotente. Sem contato por 45s proíbe novas autorizações. Reserva vence chegada 10 minutos após ACK, confirmação 30s; expiração inicia liberação, disponibilidade só retorna após reconciliação física.

## Banco e papel de execução

Migrações usam `MIGRATION_DATABASE_URL`, uma conexão administrativa direta. A aplicação usa `DATABASE_URL` pelo pooler em modo transação com prepared statements automáticos desativados. A migração cria o papel sem login `chargegrid_api`, remove acesso público e de `anon`/`authenticated`, ativa RLS e concede uma política somente ao papel da API. O administrador deve executar `GRANT chargegrid_api TO <usuario_sql_da_api>`; esse usuário não deve ser dono das tabelas nem ter `BYPASSRLS`. A Data API do schema deve permanecer desativada. Nunca conceder `chargegrid_api` aos papéis Supabase `anon` ou `authenticated`.

A versão atual exige `alembic upgrade head` até `c74ef532ab90`, que acrescenta `profiles.account_type` e `charging_sessions.created_at` preservando permissões e registros existentes. Aplicar a migração antes de publicar o código correspondente.
